## Пометки в тексте

| Пометка | Что значит | Что делать |
|---|---|---|
| `TODO (автор): …` | автор должен проверить или дописать сам | закрыть до сдачи, затем удалить пометку; найти все: `grep -n 'TODO (автор)' docs/report/*.md` |
| `[предварительные результаты, будут обновлены]` | число или вывод взяты из текущего прогона (`docs/results.md`) | заменить после нового прогона, см. ниже |
| `[N]` | ссылка на запись N в `references.md` | при добавлении источника перенумеровать |

Что можно считать **устойчивым**: описание модели данных, правил допуска,
жизненного цикла обязательства, разрешения сроков, передачи обращения и
доставки оповещений соответствует коду и меняется, только если меняется
код. **Заведомо будет меняться**: все числа экспериментов, абзац об угрозах
валидности в 2.14, разделы 1.2 и 1.4 (документация вендоров и систем памяти
обновляется часто). Главы с результатами в черновике нет: числа приводятся
только со ссылкой на раунд в `docs/results.md`.

## Как обновлять

1. **После слияния новой ветки в `main`:** `git diff <коммит сверки>..main
   -- src/duebook`, по таблице выше найти затронутые подразделы, перечитать
   их по коду и поправить. Затем обновить коммит сверки в таблице файлов
   вверху.
2. **После нового прогона эксперимента:** найти в `02-metod.md` и
   `01-obzor.md` все пометки `[предварительные результаты, будут обновлены]`,
   заменить числа и ссылки на разделы `docs/results.md`. Если прогон
   окончательный, снять пометку.
3. **Новое решение в `docs/decisions/`** (принятое владельцем): найти по
   таблице выше подраздел, к которому оно относится, описать новое правило
   по коду, добавить причины отказа в таблицу 2.3 и переходы в 2.8, если
   они изменились, и упомянуть новую версию правил в 2.4.2.
4. **Новый раунд эксперимента:** если это полный прогон всех методов на
   новой выборке, он заменяет `test3` раунда 10 как источник сравнения с
   базовыми методами в 2.14; если только нашего метода на новой
   невиданной выборке — заменяет `test5` как несмещённую оценку. Обновить
   абзац об угрозах валидности.
5. **Новый источник:** добавить в `references.md` по ГОСТ Р 7.0.5–2008 и
   перенумеровать ссылки. При нумерации по порядку первого упоминания проще
   всего добавлять новые источники в конец и переупорядочить один раз перед
   сдачей.

## Сборка в .docx

Текст написан на обычном Markdown (pipe-таблицы, формулы TeX в `$…$`) и
собирается pandoc:

```bash
pandoc docs/report/01-obzor.md docs/report/02-metod.md docs/report/references.md \
  -o report-draft.docx
```

Для оформления по требованиям ВШЭ (шрифт, поля, интервалы) передайте шаблон:
`--reference-doc=шаблон.docx`. Диаграммы состояний в 2.8 (обязательство и
условное предложение) даны двумя способами: блоком Mermaid (в .docx без фильтра `mermaid-filter` он попадёт
как код) и таблицей переходов, которая переносится без потерь. TODO (автор):
отрисовать обе диаграммы в PNG/SVG (например, `mmdc` из `@mermaid-js/mermaid-cli`)
и вставить рисунком.
